# 团队规范：API 设计

这里关注命名、抽象方式和对外 API 的可理解性。

### <span style={{ display: "inline-block", padding: "0.18rem 0.58rem", marginRight: "0.45rem", borderRadius: "999px", border: "1px solid rgba(21, 128, 61, 0.24)", background: "rgba(34, 197, 94, 0.16)", color: "#15803d", fontWeight: 800, fontSize: "0.78em", letterSpacing: "0.04em", lineHeight: 1.2, verticalAlign: "middle" }}>必须</span> 使用一致的术语

规则描述：同一个概念在同一个模块或产品域内，尽量只使用一个名字，不在 `pageCount / pageTotal / numberOfPages` 之间来回切换。

采纳理由：术语不一致会抬高阅读门槛，也会让调用方误以为不同名称背后有不同语义。

官方来源：[Effective Dart / DO use terms consistently](/effective-dart/design#do-use-terms-consistently)

相关 lints：无，主要依赖 review 执行。

### <span style={{ display: "inline-block", padding: "0.18rem 0.58rem", marginRight: "0.45rem", borderRadius: "999px", border: "1px solid rgba(180, 83, 9, 0.24)", background: "rgba(245, 158, 11, 0.18)", color: "#b45309", fontWeight: 800, fontSize: "0.78em", letterSpacing: "0.04em", lineHeight: 1.2, verticalAlign: "middle" }}>避免</span> 生造缩写

规则描述：除非缩写是团队和社区都广泛接受的常用词，否则不要为了缩短命名长度而牺牲可读性。

采纳理由：自造缩写往往只能被当下作者理解，跨模块阅读和新成员接手时成本会迅速上升。

官方来源：[Effective Dart / AVOID abbreviations](/effective-dart/design#avoid-abbreviations)

相关 lints：无，主要依赖 review 执行。

### <span style={{ display: "inline-block", padding: "0.18rem 0.58rem", marginRight: "0.45rem", borderRadius: "999px", border: "1px solid rgba(29, 78, 216, 0.24)", background: "rgba(59, 130, 246, 0.16)", color: "#1d4ed8", fontWeight: 800, fontSize: "0.78em", letterSpacing: "0.04em", lineHeight: 1.2, verticalAlign: "middle" }}>推荐</span> 让 API 读起来像自然语句

规则描述：在命名属性和方法时，优先选择让调用代码读起来顺畅、含义明确的表达方式。

采纳理由：可读的 API 命名会直接降低使用门槛，也能减少调用方误解行为的机会。

官方来源：[Effective Dart / CONSIDER making the code read like a sentence](/effective-dart/design#consider-making-the-code-read-like-a-sentence)

相关 lints：无，主要依赖设计与 review 把关。
